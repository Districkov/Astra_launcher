# 2026-10-15

## Ported tiny-ragemp-launcher into ASTRA Launcher

User request (RU): integrate the open-source `tiny-ragemp-launcher` approach
(direct connect via registry + updater offline bypass) into this launcher.

Key finding: ASTRA **already** had `write_registry` (launch2.ip/port) +
`apply_patches` + `spawn_updater` in `src-tauri/src/patcher.rs`. What was
missing was the upstream project's *domain-whitelist bypass* and a
self-contained patch table.

### What was added

`src-tauri/src/patcher.rs` (rewritten):
- `BUILTIN_PATCHES` — the 6 documented updater.exe offline-bypass patches
  (0x9393, 0x9603, 0x98CB, 0x98D9, 0xA04D, 0x99AA), used as a fallback when
  `patches_url` is unset or unreachable. Verified byte-for-byte against the
  real `C:\RAGEMP\updater.exe` (967 680 bytes).
- `resolve_patch_offset()` — content-signature search so a *newer* RAGE:MP
  updater build rebases offsets instead of failing; errors on unknown builds
  and on ambiguous (multi-match) signatures.
- `apply_patches()` is now idempotent (skips already-applied patches).
- `HostsEntry` / `build_hosts_body()` / `apply_hosts_mapping()` — hosts-file
  whitelist bypass tagged with `# astra-launcher`, preserving foreign lines.
- `is_whitelisted_domain()` — mirrors the `*.gta5rp.com` / `*.grandrp.com` rule.
- RUI auto-connect (`inject_rui_auto_connect`): length-preserving payload
  written into `rui\index.rui`. **Bounded to 4096 bytes and requires a
  newline-delimited window**, so minified bundles are refused rather than
  corrupted. Always backs up to `index.rui.astra.bak` first; `restore_rui_backup()`
  undoes it.

`src-tauri/src/main.rs`:
- New commands: `get_patch_manifest`, `check_patch_status`,
  `get_whitelist_status`, `set_connect_mode`, `apply_whitelist_bypass`,
  `remove_whitelist_bypass`, `restore_rui`.
- `resolve_patch_manifest()` — server manifest → built-in fallback.
- Elevation pattern: **no sidecar binary**. The app relaunches *itself* via
  `ShellExecuteW(... "runas" ...)` with `--hosts-apply <ip> <domain>` /
  `--hosts-clean`; `handle_cli_mode()` short-circuits in `main()` before Tauri
  initialises and exits with a status code. Requires the new
  `Win32_UI_Shell` + `Win32_UI_WindowsAndMessaging` windows-crate features.

`src-tauri/src/config.rs`: added `connect_mode` (`raw` | `hosts`) and
`hosts_domain` to `LauncherConfig`.

Frontend: `types.ts` (PatchManifestResponse, PatchStatusResponse,
WhitelistStatusResponse, ConnectMode), `gameStore.svelte.ts` (patch/whitelist
state + actions, launch phase renamed to "Патч updater.exe"),
`Settings.svelte` (two new diagnostic cards), `App.svelte` prop wiring.

### Verified

- `vite build` — succeeds.
- Patch table applied to a *copy* of the real updater.exe: all 6 validate,

## Binary analysis: can `updater.exe` be skipped? (answered, not implemented)

Reverse-engineered the real install at `C:\RAGEMP` by extracting ASCII **and
UTF-16LE** strings (registry value names are wide strings — searching ASCII
alone gives false negatives).

### `updater.exe` (967 680 bytes) — pure updater
Strings: `RAGE Multiplayer Updater`, `updater.pdb`, `ShellExecuteExW`,
`sha256//`, libcurl/OpenSSL, `RAGE-MP Updater`.
**Zero** `launch*` strings. **Zero** `Software\RAGE-MP`.
→ It only downloads files and calls `ShellExecuteExW` to start the client.

### `ragemp_v.exe` (21 242 680 bytes) — the real client
- CEF/Chromium host (`disable-webgl`, `disable-3d-apis`, `disable-dev-tools`, …)
- Reads `Software\RAGE-MP`: `launch.ip`, `launch.port`, `launch.type`,
  `launch.password`, `launch.data0`, `launch.cefPort`, `game_v_path`,
  `rage_path`, `player_name`
- Locates GTA V via `SOFTWARE\WOW6432Node\rockstar games\GTAV` / `…GTAV
  Enhanced` / `…Grand Theft Auto V` (`InstallFolder`, `InstallFolderEpic`),
  plus Steam paths
- `common.rpf` (game presence check), `connect` (a launch type),
  `Failed to find the game.`, `Failed to inject into game launcher`,
  `ragemp_v.exe`, `updater.exe.old` (self-update rename dance)
- Exposes the CEF JS API. `app.js` (1 184 165 bytes, index 262 in the archive)
  calls 15 `rageApi.*` methods, notably **`rageApi.launchGame`** and
  **`rageApi.isALauncher`** — an official "started by an external launcher" flag.

### Conclusion
`updater.exe` **can** be skipped: the registry read, UI and game injection all
live in `ragemp_v.exe`. Going straight to it would bypass the CDN check
entirely, making the 6 patches unnecessary.

### Open questions (need an empirical test)
1. `ragemp_v.exe` contains `Failed to start updater` /
   `Please run updater.exe as admin.` — it may try to spawn `updater.exe`
   itself. Behaviour when the file is missing is unknown.
2. **`launch2.*` vs `launch.*`.** Upstream (and the current ASTRA code) write
   `launch2.ip` / `launch2.port`, but `ragemp_v.exe` contains only
   `launch.ip` / `launch.port` — **no `launch2` anywhere**, in either encoding.
   Either the key was renamed in a newer build, or `launch2` is read by a
   component not in this binary. **This may mean the current direct-connect
   path is silently failing on this build** — worth testing before trusting it.
3. `launch.type` accepted values — `connect` is the likely one for direct join.
4. EAC + Rockstar auth remain hard dependencies either way.

## Binary analysis: images in `ragemp_v.exe` (answered, not implemented)

### `ragemp_v.exe` is Authenticode-signed
- Certificate table at file offset `0x143FA00`, length 10552
- **GlobalSign EV Code Signing** (`GlobalSign GCC R45 EV CodeSigning CA 2020`),
  Private Organization, Greater London, valid 2023-08-03 → 2026-08-03
- Authenticode covers every byte except the signature table itself, so **any**
  edit invalidates it → Windows "unknown publisher", SmartScreen warnings, EAC
  may refuse to run, and RAGE:MP's own updater will re-download the file.

### Resource inventory (`.rsrc` @ raw `0x143C200`)
| Type | Count | Size |
|------|-------|------|
| `ICON` | 1 | 1643 |
| `GROUP_ICON` | 1 | 20 |
| `VERSION` | 1 | 784 |
| `MANIFEST` | 1 | 1194 |

**Exactly one image is embedded**: a 256×256 PNG at `0x143c330`, 1643 bytes.
Its SHA-256 is **identical** to the image inside `C:\RAGEMP\mp.ico`
(`3ec9a55de60197adbd369806f7b1c044…`) — the same 256×256 32bpp artwork.

Note: signature scans for `BMP`/`ICO`/`JPEG` byte patterns in the exe are
**false positives** — `BM`, `\x00\x00\x01\x00` and `\xff\xd8\xff` are extremely
common in machine code. The only real hit is the single PNG.

### Images that live on disk (safe to replace)
| File | Size | Dimensions |
|------|------|-----------|
| `mp.ico` | 1665 B | 256×256, 32bpp |
| `mp.png` | 786 B | 256×256 |
| `rui/cursor.png` | 3155 B | 17×24 |
| `EasyAntiCheat/SplashScreen.png` | — | EAC-owned |

### Conclusion
Changing "images in ragemp_v.exe" means changing the app icon — one 256×256
PNG — and it breaks the signature. **Not worth it.**

The images a user actually sees in the RAGE:MP launcher live in
**`rui/index.rui`** (~263 entries: backgrounds, loader bar, logos). Those are a
*data file* read at runtime, **not** covered by the exe signature — which is
exactly why the RUI editor in `src-tauri/src/rui.rs` is the safe route, and why
it backs the archive up before writing.

### Signing is NOT done — needs a password
`tauri.conf.json` has `createUpdaterArtifacts: true`, so the build ends with:

> A public key has been found, but no private key. Make sure to set
> `TAURI_SIGNING_PRIVATE_KEY` environment variable.

`.tauri-keys/private.key` is a Tauri **encrypted** rsign key
(`untrusted comment: rsign encrypted secret key…`, 348 B, single line).
Signing without `-p/--password` exits 1 with no output — it is waiting on a
password prompt. **The password is not stored anywhere in the repo.**

auto-updater will reject it, because `tauri-plugin-updater` verifies the
minisign signature before installing. To ship a release that can self-update:

```bash
TAURI_SIGNING_PRIVATE_KEY_PASSWORD='<password>' \
  npm run tauri build
# or sign an existing artifact:
node_modules/.bin/tauri signer sign -f .tauri-keys/private.key -p '<password>' <file>
```

Then regenerate `latest.json` (the `scripts/create-release.ps1` flow, which
also uploads via `gh`).

## Bug fix: "бесконечная проверка сервера" — v1.11.1

User reported the launcher stuck on an endless server check.

### Root cause found in `launcher.log`
```
[22:09:24] get_server_status: querying 185.176.94.21:30120
[22:09:29] info.json request failed      <- full 5s timeout
[22:09:34] players.json request failed   <- another 5s
[22:10:02] get_server_status: querying   <- x3, polls overlapping
```

Four compounding problems:

1. **Wrong port.** `%APPDATA%\astra-launcher\config.json` had
   `server_address: "185.176.94.21:30120"` — **30120 is the FiveM port**.
   RAGE:MP uses **22005**. This value is written straight into `launch.port`,
   so the client was being told to connect to nothing. Left over from the
   legacy FiveM-era schema; my v2 migration preserved it as-is.
   → Fixed the config in place (backup at `config.json.bak`).
2. **Sequential requests, 5s each.** `info.json` then `players.json` = 10s
   total, which is exactly the poll interval → requests piled up forever.
3. **No in-flight guard** in `serverStore`, so overlapping polls were possible.
4. **Play button blocked.** `disabled={isLaunching || !serverOnline}` — with a
   server that never reports online, the user could *never* launch. For a
   project whose whole point is reviving a dead platform, gating launch on a
   stats endpoint is exactly wrong.

### Fixes
- `server.rs`: both requests via `tokio::join!` (concurrent), timeout 5s → 3s.
  Added a **TCP fallback** — if HTTP stats fail but the game port accepts a
  connection, the server counts as online. New response fields
  `reachability` ("http"|"tcp"|"none"), `has_stats`, `ping`.
- `serverStore`: `statusInFlight` / `pingInFlight` guards; tracks
  `reachability` and `hasStats`.
- `PlaySection`: Play is now `disabled={isLaunching}` only. Offline shows an
  advisory line ("Server stats unavailable — you can still launch") instead of
  blocking.
- `diagnose_launch`: warns when the port is 30120.
- New `set_server_address` command with validation (host/IP + port, rejects
  scheme prefixes, flags 30120) and a **"Адрес сервера"** field in Settings —
  previously the address was only editable by hand-editing config.json.
- i18n ru/en for all new strings.

### Verified
`http://185.176.94.21:30120/info.json` and `:22005/info.json` both time out,
but TCP connects on both. So HTTP stats are simply not served by this server —
the TCP fallback is what makes it report online.

## Bug fix: window "не отвечает" (UI freeze) — v1.11.2

User reported the window frequently going to "Not Responding".

### Root cause
In Tauri, a command declared as a plain `fn` runs **on the main thread** and
blocks the UI. 27 of the commands in `main.rs` were synchronous, and several do
serious work:

| Command | Why it was expensive |
|---|---|
| `get_rui_status` | read + `Archive::parse` of the **15 MB** `index.rui` (265 allocations + 15 MB memcpy) |
| `preview_rui_config` / `apply_rui_config` | same full parse (apply also rewrites 15 MB) |
| `restore_rui` | copies 15 MB |
| `auto_find_rage_dir` / `get_rage_dir` | walks several directory trees and **spawns PowerShell** per `.lnk` |
| `diagnose_client_install` | recursive file counting |
| `get_whitelist_status`, `diagnose_launch` | filesystem + registry |

Compounding it, `Settings.svelte`'s `$effect` fired **five** of these at once on
mount, and `App.svelte`'s `onMount` fired nine more in parallel.

### Fixes
1. **`rui::inspect()`** — new header-only metadata reader. Reads the two tables
   plus the first 8 bytes of each entry; cost is proportional to entry count,
   not archive size. `get_rui_status` now uses it instead of a full parse.
   Verified it agrees with `Archive::parse` on both the synthetic archive and
   the real 15 MB one.
2. **Every filesystem/registry command is now `async` + `spawn_blocking`** via a
   small `blocking(what, f)` helper that maps join errors to strings. Converted:
   client (5), whitelist (1), launch path (3), server address (1), RUI (6),
   discord (2), username (2), config (1), onboarding (2).
3. **Frontend sequencing.** `Settings.svelte` now loads its five diagnostics
   one after another with a cancellation guard. `App.svelte` chains
   `loadRageDir().then(autoFindRageDir)` so the two expensive directory walks do
   not compete.
4. Removed the now-unused `patcher::read_registry` shim.

### Verified
36 Rust tests pass · `cargo check` no warnings · tsc clean · vite builds ·
installer rebuilt.

Installer: `ASTRA_Launcher_x64-setup.exe` — v1.11.2, 6 547 264 B, unsigned.

  `save_rage_dir()` returns `(normalised_path, valid)` and writes both keys.
- `Settings.svelte` + `onboardingStore`: use a **directory picker**, consume
  the backend's normalised `path` + `valid`, and never show success for an
  unrecognised folder.
- `main.rs`: `set_rage_dir` now returns a result object so the UI can validate.
- Fixed user's live `%APPDATA%\astra-launcher\settings.json`:
  `rage_dir` and `rage_client_path` = `C:\RAGEMP`; backup at
  `settings.json.bak`.
- Fixed `package-lock.json` — it was stale at v1.6.8 while package.json had

- Also converted remaining synchronous Tauri FS/registry commands to async +

## 2026-10-16: 404 again even with the length-preserving splice — XXH64 — v1.13.1

The equal-length splice **still** 404'd. That ruled out the offset-shift
theory: same archive size, same every table offset, only 225 bytes of `app.js`

### The real header format (cracked it)
The 8488-byte header is **32 bytes per entry**, not 16:

| field | offset within record | notes |
|-------|----------------------|-------|
| `size` u32 | `+0` | what our parser already read |
| **`XXH64(content)` u64** | `+8` | **never updated by us → the bug** |
| `offset` u32 | `+16` | what our parser already read |
| `XXH64(name)` u64 | `+24` | name hash; unchanged by an edit |

- Table 1: 132 records at `0x10 + 32k` (ends exactly at 4240)
- Table 2: 133 records at `4240 + 32k` (last record's `+24` field runs past
  HEADER_END — the table is effectively truncated, which is why a naive
  133 × 32 parse blows up)
- Extra untouched regions reported earlier (`2128..4240`,
  `6368..8488`) are simply the hash halves of those same records — there is
  no separate table.

**Proof:** `stored == XXH64(blob)` held for **263 of 264** entries on the
shipped archive, and the *only* mismatch was the entry we had spliced. Then
the whole factory archive verified **265/265** once restored.

### Why upstream `build.py` "worked"
It grows `app.js` too — and never updates the hashes either. It has the same
latent bug; it just happened to go unnoticed.

### Fix
- `rui.rs`: new `xxh64()` (full XXH64, seed 0) + `Entry::hash_pos`.
- `Archive::serialize()` now writes `XXH64(blob)` at `hash_pos` for every
  entry alongside size and offset. Range-checked.
- Module doc rewritten with the correct 32-byte layout and the two hash
  fields, plus the splice-vs-rebuild rationale.

### Verified

`xxh64_matches_known_vectors` (reference vectors),

**A/B test done and decisive.** Factory RUI + `rui_ac=false` (launch 14:09:41) →

### Correlation found in the CEF log

from the working 14:09–14:11 session. That is the actual failure: the renderer

```js

  /*astra-connect*/setTimeout(()=>{try{this.launchGame({ip:"185.176.94.21",port:22005},!0)}catch(e){}},2000),
  this.loader("core",!1)   …spaces… }
```

Payload 129 B into a 178 B region; `app.js` 1 184 165 B and archive 15 695 568 B
both unchanged; 0 bad hashes; `node --check` OK. 59 Rust tests pass.

### Format note worth remembering
The `+24` name-hash field is offset by one entry relative to the record you
would expect: record *i*'s `+24` holds the name hash of the entry at record
*i+1* (verified: the 712-byte `<!DOCTYPE html>` entry carries
`js/app.1950bf4f.js`, the SVG below it carries `index.html`). Since an edit never
touches `+24`, this is harmless, but it makes a naive "name hash → index" lookup
wrong.

## 2026-10-16: app.js is effectively immutable — switch to index.html — v1.13.4 (untested)

What has been ruled out about `app.js`, with evidence:
- growing vs equal-length (both 404)
- offset shifting (equal-length, offsets identical)
- XXH64 content hashes (all 265 verified valid; the client does read them —
  a stale hash 404'd too)
- JS syntax (`node --check` passes on the exact bytes the Rust emits)
- anchor uniqueness and placement
- removing `await this getServers` (preserving it changes nothing)
- hardcoded hash in the binaries: the factory `app.js` XXH64

  `cef\ragemp_ui.exe` and `cef\ragemp_game_ui.exe`
- header magic `0x32721aafd46b32c8` is **not** XXH64 of the header, of the

The only part of the header never decoded is `2128..4240` (2112 B). It contains
16-byte records of `(val, 0, u64)` where `val` alternates between known sizes and
known offsets — i.e. it looks like the *other halves* of the 32-byte records,

That region is the remaining suspect, but decoding it needs a disassembler.

## 2026-10-16: ROOT CAUSE FOUND — the menu is intentional for raw IPs — hosts mode

The user pointed out a friend runs `tiny-ragemp-launcher` (the upstream project
we ported) and it works. Reading its README revealed the missing sentence:

> "`ragemp_v.exe` has a hardcoded domain whitelist for `launch2.ip` registry
> values — only `*.gta5rp.com` and `*.grandrp.com` subdomains pass. Custom
> domains like `play.xxxx.com` get rejected silently (**registry cleared,
> server browser loads instead of direct connect**)."

**So the menu was never caused by our RUI patches.** Writing a raw IP
(`185.176.94.21`) into `launch.ip` / `launch2.ip` *deliberately* makes the
client clear the registry and show the browser. Every one of our A/B tests
compared "factory RUI" against "edited RUI" while **both ran in `connect_mode:
raw`** — the variable that actually matters was never touched. That is why the
factory baseline showed the menu too, and why the 404 on edited builds was a
separate real bug that got confused with this.

The fix needs no RUI edit at all: hosts-file mapping of a whitelisted domain,
which ASTRA already implements (`connect_mode: hosts` +
`is_whitelisted_domain` = `*.gta5rp.com` / `*.grandrp.com`).

### What was configured
- `connect_mode` → `hosts`, `hosts_domain` → `astra-185-176-94-21.gta5rp.com`
  (matches the launcher's own default `astra-<ip-with-dashes>.gta5rp.com`)
- `rui_auto_connect` → `false`; factory `index.rui` still on disk
- The hosts line (`185.176.94.21 astra-185-176-94-21.gta5rp.com`) could **not**
  be written from the agent: the sandbox blocks `Add-Content`, `Start-Process`
  and COM elevation. Use ASTRA's own Settings → «Белый список» → «Применить»,
  which writes it natively via `ShellExecuteExW(runas)` from Rust.

### Note for the future
`ragemp_v.exe` contains **no** masterlist URL at all — the server list is
fetched by the JS inside `index.rui`. And `%LOCALAPPDATA%\CEF\User Data` holds
only Crashpad/Dictionaries/WidevineCdm, so there is no external reference hash
cached anywhere: the reason a rebuilt archive is rejected is still unexplained,
but it no longer matters, because there is no reason to edit the archive.
