## Path B scaffolding for the "secure connection" fix (same day)
Diagnosis confirmed: the server (89.35.130.191:22005) works on raw IP via the
stock RAGE:MP browser, but auto-connect via `launch2.ip` is rejected by
`ragemp_v.exe`'s whitelist (only `*.gta5rp.com`/`*.grandrp.com`), and the
hosts-fake-domain workaround breaks the secure (TLS) connection. So the clean
fix is to **byte-patch `ragemp_v.exe` to neuter the whitelist check**, letting
`connect_mode: "raw"` write the raw IP.
Implemented the ASTRA side (compiles, inert when empty):
- `config.rs`: new `ragemp_v_patches: Vec<Patch>` field (serde default, loaded
  from config.json, saved back, empty default → no behavior change).
- `patcher.rs LaunchOptions`: `ragemp_v_patches` field + Default.
- `patcher.rs launch_ragemp`: new step 3b applies `apply_patches(ragemp_v.exe)`
  before spawning the updater; warn-only if missing/fails.
- `main.rs launch_patched`: passes `CONFIG.ragemp_v_patches` into LaunchOptions.
- `Patch` is imported into config.rs (`use crate::patcher::Patch`).
KEY: `resolve_patch_offset` scans the binary for the `original` bytes when the
reference offset misses, so the user only needs the jump bytes + a little
context (no RVA→file-offset math); uniqueness via surrounding bytes.
BLOCKER: the actual whitelist-bypass bytes must be extracted by RE on the test
machine (ragemp_v.exe + a disassembler are absent on this dev box — rage_dir is
empty). Procedure handed to the user (x64dbg: find `.gta5rp.com`/`.grandrp.com`
strings → xref → conditional jump at the gate → flip to unconditional jmp/NOP).
Next: user supplies bytes (or pastes ragemp_v.exe) → wire + build v1.13.6.
